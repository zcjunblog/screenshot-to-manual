## 2. 问题与产品定位

用户已经有操作截图，但仍需反复整理顺序、写步骤、标注按钮并制作培训文档。项目将这套重复工作封装为可复用 Skill，交付能编辑、阅读和移交的图文手册。

目标用户：客户实施人员、软件交付团队、客服、行政、人事培训人员、教程作者，以及需要向他人说明操作步骤的人。

核心承诺：上传截图和简要说明，得到有截图依据的操作说明；截图无法证明的步骤清楚标记，不通过编造补齐流程。

## 3. 首版范围

### 输入

- 用户提供的 PNG/JPEG 截图，支持电脑页面和手机界面混合输入的验证。
- 简短任务目标、目标读者和用户已知的操作顺序；可选品牌名及文档标题。
- 现有文字步骤可作为依据，与图片冲突时单独列出。
- 以用户顺序或明确编号为首选；文件时间、文件名与视觉状态只能提供排序线索。
- 暂以 3～20 张截图作为验证样例规模，不把它宣称为已验证产品容量。

### 输出（v0.1.0已实现）

1. 可编辑 `操作手册.docx`。
2. 便于阅读和打印的 `操作手册.pdf`。
3. 可移交的 `操作手册.md` 与相对路径图片目录。
4. `待补充信息.md`：缺失步骤、模糊文字、排序疑问和待确认内容。
5. 内部步骤清单：连接步骤、截图、标注和依据，供检查与修订使用。

Word使用可选python-docx，PDF使用LibreOffice转换；三种尺寸基础样例9页检查已通过，新增三套模板同内容样张共12页已逐页检查。原图留在用户输入目录，不默认包含在可外发交付包中。

## 4. 手册结构

- 标题、目标读者、用途、生成日期及软件版本（用户未提供则标记未知）。
- 前置条件：仅列有来源的账号、权限、材料或环境要求。
- 编号步骤：操作目的、对应截图、操作对象、动作、输入内容说明、预期状态。
- 常见问题与检查要点：仅使用资料支持的内容；建议与既定事实分开。
- 待确认或待补图清单；未解决的关键缺口使文档保持“草稿”状态。

每一步原则上描述一个明确动作或一组紧密相关动作。步骤过多时按任务阶段组织，不能为凑页数拆分。

## 5. 工作流程

1. 登记图片清单、尺寸和方向，检查能否读取、是否重复和是否存在明显敏感信息。
2. 读取任务目标和现有说明；识别每张截图的可见界面、控件、文字和状态。
3. 生成候选步骤顺序，区分已明确顺序与推断顺序；重复截图不直接删除。
4. 检查缺失环节、图片与文字矛盾、模糊控件与无法推断的输入内容。
5. 展示简洁步骤提纲；集中询问阻塞准确性的排序或操作问题，其余缺口保留可见。
6. 在图片副本上制作准确编号、框选或局部放大；按用户要求处理敏感区域。
7. 根据结构化步骤生成 Word、PDF 和 Markdown 文件。
8. 逐页检查产物与原截图是否一致，检查资源是否齐全，交付文件及剩余限制。

## 6. 步骤数据与图像处理要求

步骤记录至少包含：`step_id`、`title`、`source_image`、`source_note`、`action`、`target`、`expected_result`、`evidence_status`、`annotations`、`open_questions`。

- 每个关键动作应来自用户说明或截图可明确支持的信息；相邻截图状态变化不必然证明中间操作。
- 原图尺寸与标注坐标绑定；缩放、裁切后必须同步变换坐标并校验边界。
- 不生成伪造界面，不修改按钮名称或界面真实文案。
- 标注采用Pillow确定性图像处理，不依赖生成模型重绘软件截图。
- 无法准确定位的控件以文字引用并标记待确认，不能猜位置。
- 敏感内容遮盖应真正移除导出图片中的对应像素，避免用可撤除的文档遮罩冒充脱敏。
- 检查 DOCX/PDF 包内嵌资源，不夹带未脱敏原图；不承诺全自动识别所有敏感信息。

## 7. 方案选择

| 方案 | 优点 | 代价与限制 |
| --- | --- | --- |
| 纯文本与图片拼排 | 依赖少、易验证 | 文档观感和步骤定位较弱 |
| 图像理解 + 结构化步骤 + 确定性标注与文档模板 | 可编辑、可追溯、适合正式交付 | 需验证标注坐标、字体与导出 |
| 自动录屏或操作捕获 | 能获得更多过程证据 | 需要扩展、权限、跨系统维护，超出首版 |

已按用户确认采用第二种，首版只消费用户已有截图。录屏、自动点击和浏览器扩展作为独立后续方向，不与本版混合承诺。

## 8. 失败处理与边界

- 图像不可读或文字模糊：指出具体图片和区域，请用户补充，继续处理其他可读图片。
- 顺序不确定：说明依据和不确定点，不把模型猜测写成已验证流程。
- 缺失关键界面：生成带缺口的草稿，不补造截图或软件操作。
- 截图显示成功不等于实际业务完成；只描述可见成功提示，不验证后台数据。
- 未提供账号权限或产品版本时，不推定所有读者都有相同操作入口。
- 不覆盖原图、不自动登录、不采集其他窗口、不发布或发送教程。
- 生成失败时返回具体失败环节和已有可用产物，不输出无法打开的伪成功链接。

## 9. 命名与市场展示

- 中文展示名：截图转操作手册。
- 英文工作名：Screenshot to Manual。
- 拟定简介：上传操作截图和简要说明，生成带步骤编号、重点标注与检查要点的图文手册，适用于软件交付、员工培训和客服教程。
- 自然覆盖词：截图、操作手册、使用说明、图文教程、操作指南、软件培训、SOP。
- SOP 仅作使用场景，不承诺仅凭截图编写完整企业制度。
- 示例指令：
  - “把这些后台操作截图整理成给新员工看的图文手册。”
  - “按我标的顺序生成客户使用说明，标出需要点击的位置。”
  - “检查这些截图是否缺步骤，先列问题，再做教程草稿。”
- 不使用“一键零错误”“全自动录制”等超出能力的宣传。

## 10. 验收与验证样例

拟制作桌面管理后台、移动端操作、跨页面培训流程三组演示材料，并加入乱序、重复、缺图、模糊和敏感字段变体。

发布前至少满足：

- 每个步骤对应正确截图，按钮文案与来源一致，没有虚构界面或无依据的动作。
- 预埋缺失步骤与顺序冲突被识别，关键缺口未解决时文档保留草稿标记。
- 标注位置正确，不遮挡文字，无越界或裁切后漂移。
- Word 可打开和编辑；PDF 页面可渲染，中文无乱码、图片清晰、无明显溢出或空白异常。
- Markdown 与图片一并移交后可阅读，无开发机绝对路径依赖。
- 脱敏后的交付包未包含测试用敏感字符串或未脱敏原始图片。
- 重复运行不修改输入，不覆盖已生成的旧版本。
- 至少一次真实 WorkBuddy 导入与端到端运行，记录客户端版本与依赖。
- 找未参与制作的人照着手册完成演示任务，记录卡点并修订；没有该验证时不能声称用户可顺利完成。

## 14. v0.1.0工程决策与验证

- Python3.9+；Pillow负责图片，python-docx和LibreOffice为Word/PDF可选能力；开发完整环境为Python3.12.14、Pillow13.0.0、python-docx1.2.0。系统Python3.9缺Pillow时doctor明确报告，不能生成图片包。
- 原图1至20张、每张10MiB、4000万像素、累计1.2亿像素；最多60条步骤。模型JSON不超过5MiB。说明按非空行建立N编号，动作和预期状态的user_note要求精确连续引文。
- privacy按图片统一复核和遮盖，处理顺序为同一份摘要校验字节快照、EXIF归正、透明度合成白底、像素遮盖、裁切和边框标注。编号在图外40像素留白中，窄图扩展画布；不把标注文字盖在原界面上。
- Word采用A4白蓝办公视觉、黑色标题、蓝色步骤编号和截图标注。office采用信息摘要/总览并允许短步骤同页，delivery采用独立封面与分步分页，training采用大图优先和操作/检查分离；图片等比限制尺寸，长步骤自然跨页。可使用STM_CJK_FONT指定已安装中文字体。
- 标准与WorkBuddy双包共用单一源码和VERSION；安装器支持七类目录与自定义--dest、备份替换。发布字段按官方文档核对，中英文示例均3条。
- 本地虚构演示程序真实运行并由独立无头Chrome截图，DPR2；包含桌面、手机和混合尺寸三个变体，同一业务流程，不算三个独立行业案例。ChromeDevTools连接器被已有实例占用，使用宿主bundled Playwright启动独立无头Chrome完成开发截图；不访问账号或其他页面。
- 51项完整依赖测试通过，标准库环境12项分发测试通过。双包各3组独立解压运行通过，基础Word/PDF三份共9页、模板对照三份共12页完成逐页检查及内嵌资产核对。
- 独立审查4项发现均已补失败回归并修复：透明隐藏像素显露、缺少image_id键、摘要/读取竞态、窄裁切编号丢失。另修复异常摘要类型检查。语义、完整脱敏、更多软件和实际读者体验仍需验证。
- 对外移交ZIP含实际成功的文档和派生图片，内部模型/来源索引不进入ZIP；所有产物保持草稿标记。示例可查看examples/sample-manual。

客户端首轮反馈：存在步骤冗余及手写图号错位，已强调实际动作合并、按来源ID引用、只保留当前目标缺口，并要求改模型后统一重导出。不得只改Markdown造成格式不一致。多区域编号与同色边框对应，保留正文控件描述。
